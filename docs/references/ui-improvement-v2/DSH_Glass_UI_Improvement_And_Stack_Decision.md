# DSH Glass — 液态玻璃 UI 整改报告与技术栈迁移决策书

> **版本**：v2.0 · 2026-10-17  
> **交付对象**：Codex / 编程 Agent  
> **适用项目**：Windows 桌面 DSH Glass 悬浮伴侣  
> **当前技术栈**：以仓库实际实现为准；预期为 Electron + React + TypeScript  
> **决策原则**：**给现有技术栈一次明确、可验收的整改机会。整改仍无法达到用户要求时，不再反复微调 CSS，立即进入 Tauri 2 对照原型；对照实测合格后迁移。**

---

## 0. 开发 Agent 必须先执行的指令

这是**整改与迁移决策书**，不是单纯的界面参考文案。

1. **先审计实际仓库**：找出窗口创建、背景材质、原生接口、DOM 层级、主题 Tokens、窗口尺寸/动画、任务 Todo、审批面板、DSH Bridge、Mock 数据及测试入口。不得假定文件存在或凭空填写实现结果。
2. **先建立基线，再修改代码**：在真实 Windows 桌面捕获当前效果，记录 Windows Build、DPI、Electron/Chromium 版本、GPU/硬件加速状态、背景材质、窗口配置和资源占用。
3. **严格按本报告规定的一次整改周期实施**，不要持续交付若干次只有渐变、模糊半径变化的版本。
4. **通过真实桌面截图和功能测试评价成果**。浏览器预览、Figma 图、AI 生图不能代替桌面实际渲染。
5. **保护现有 DSH 数据和审批能力**：任务状态、Todo、审批队列、Bridge 协议、Mock、窗口拖动/缩放/置顶/托盘等必须保持工作。不能为了好看伪造审批成功。
6. **如果验收不达标**，输出失败原因和证据，停止当前 UI 微调，执行本报告第 9 节的 Tauri 2 原型比较；只有 Tauri 对照符合切换门槛才迁移正式产品，否则提交限制报告和第三路线建议。
7. 交付必须包含修改文件清单、真实截图、测试命令与结果、问题列表、用户需要确认的决策，不得仅报告“已完成优化”。

### 总目标（不可歪曲）

> 将“深色磨砂卡片叠在灰色大窗口上”的界面，改造成“**单块通透、轻盈、带局部光学边缘的液态玻璃对象**”。正常态只出现任务标题、必要的进度和当前步骤；审批时才临时生长出安全、完整、可读的操作界面。

用户偏好是：iOS Liquid Glass 风格的**通透透亮、清澈、柔和光学反射、灵动形变、极简信息结构**。不是深色玻璃拟态，不是传统 Dashboard，也不是灰色 Acrylic 蒙层。

## 1. 本次反馈依据与问题诊断

### 1.1 随包视觉证据

- 现有 UI 截图：`assets/current-01.png` ~ `assets/current-04.png`；
- 用户认可的视觉方向：`assets/visual-target.png`。

这些图片应当用于**方向对比和人工评价**。参考图是理想化渲染，不代表 Electron 或 Tauri 可直接复制其折射、场景和强光斑；判断成败必须依据真实 Windows 桌面捕获。

### 1.2 已确认的设计缺陷（从截图观察，非源码诊断）

| ID | 缺陷 | 现象 | 为什么严重 | 改造要求 | 优先级 |
|---|---|---|---|---|---|
| V-01 | 主体混浊 | 大面积灰色/棕灰色蒙层，缺乏背景空间感 | 看起来像磨砂塑料而非薄玻璃 | 减少全局实色遮罩；重新验证系统材质与透明合成 | P0 |
| V-02 | 深色嵌套面板 | 标题、任务、审批命令被深蓝色大矩形包裹 | 制造“玻璃里面嵌塑料板”的割裂感 | 去除普通态全部深色实心卡片 | P0 |
| V-03 | 信息层级臃肿 | 标题、进度、状态、重复容器和按钮占空间 | 不像悬浮伴侣，更像小型控制台 | 常态只保留标题/进度/当前步骤 | P0 |
| V-04 | 边缘没有光学质感 | 厚重灰色轮廓，局部高光不精细 | 缺少水晶薄边、反射、景深层次 | 细化边缘、高光、淡色散，避免霓虹描边 | P1 |
| V-05 | 审批内容裁切 | 长审批卡片底部操作按钮被截断或挤压 | 直接影响操作安全 | 固定审批操作区，正文独立滚动 | **P0 阻断项** |
| V-06 | 阅读层级不佳 | 工具命令卡片巨大，“打开 DSH”按钮过于显眼 | 次要操作抢占主要决策空间 | 命令简短预览，完整详情按需展开；审批操作优先 | P0 |
| V-07 | 动态灵动感未知 | 静态图不能证明形变质量 | 可能只是在切换两个尺寸 | 必须实际录屏验证连续变形和交互反馈 | P1 |
| V-08 | 窗口真实材质未证实 | 无法从截图确认后台是 Acrylic、Mica、CSS 还是截图模拟 | 改 CSS 可能无法触及根因 | 审计具体窗口合成路径，做 A/B 实验 | P0 |

### 1.3 明确不允许的补救方式

- 不允许通过**增加全局灰白不透明度**来掩盖透明材质难题。
- 不允许把深蓝大卡片改成浅蓝大卡片，换颜色但保留多层容器结构。
- 不允许为证明“更亮”而把所有边缘做成高强度发光、彩虹光带。
- 不允许把用户认可的设计图作为背景图片贴在窗口里冒充真实玻璃。
- 不允许未经授权使用屏幕捕获、壁纸截图或显示器采样来伪造窗后背景。
- 不允许因为布局改造就隐藏审批按钮、完整命令、错误提示或离线状态。

## 2. 目标设计：一块玻璃，按需变形

### 2.1 极简信息策略

**常态只保留：**

1. 当前任务标题（核心）；
2. `已完成步骤/总步骤` 或微型进度条（只有准确 Todo 数据才显示）；
3. 当前正在执行的步骤（有可靠状态时显示）；
4. 待审批数量（仅在有待处理操作时出现）。

**删除常驻显示：** Logo、`DSH Glass` 品牌栏、`MOCK` 徽章、连接成功状态、最小化/关闭按钮、`置顶`/`退出`、`活动与设置`、`bash`、`只读` 等无上下文标签。

**迁移操作入口：** 右键菜单或系统托盘。异常/断线时要主动提示，不能因为删除连接标识而隐藏故障。

### 2.2 UI 形态定义（逻辑像素参考，非硬编码）

| 模式 | 推荐尺寸 | 显示内容 | 切换方式 |
|---|---:|---|---|
| `capsule` 极简胶囊 | 250~340 × 50~64 | 状态光点 + 标题 + 可选进度 | 默认/手动收起 |
| `peek` 任务速览 | 320~420 × 130~220 | 标题 + 极细进度 + 当前步骤 + 可选审批提示 | 单击/用户配置 |
| `expanded` 完整任务 | 360~520 × 270~560 | Todo 列表，当前步骤高亮 | 主动展开或拖动放大 |
| `approval` 审批 | 380~560 × 320~640 | 请求概要 + 完整详情入口 + 固定决策栏 | 有待审批且允许自动展开 |

窗口缩放改变信息层级，不允许将整个面板仅用 `transform: scale(...)` 缩小。

### 2.3 推荐信息原型（结构，不是最终材质）

**默认/速览：**

```text
╭────────────────────────────────────────╮
│ 构建 DSH Glass 悬浮伴侣         1/2  ⌄ │
│ ━━━━━━━━━━━━━━━──────────              │
│ ◉  验证悬浮窗与状态同步                │
│                                        │
│  ⚠ 1 项操作需要确认                 →  │
╰────────────────────────────────────────╯
```

注意：最后一行审批提示仅在真实存在请求时出现，且它是**唯一可以使用单独浅玻璃胶囊的区域**。任务标题、进度、步骤直接浮在主玻璃上。

**审批：**

```text
╭────────────────────────────────────────╮
│ 需要你的确认                            │
│ 构建 DSH Glass 悬浮伴侣                │
│                                        │
│ 终端命令                               │
│ echo "DSH Glass preview"              │
│ [查看完整命令/路径/请求详情]            │
│                                        │
│ ────── 以下操作区固定不滚动 ─────────── │
│ [拒绝]                  [允许一次]     │
╰────────────────────────────────────────╯
```

- 正文可滚动；顶部标题和底部审批决策区域独立于滚动区域。
- 若只有参数**预览**而完整操作信息不可获得，必须明确提示，并将不能安全确认的决定留在 DSH 原窗口执行；不能把不完整信息包装成可直接批准。
- 每项审批根据 `sessionId + requestId` 区分，多请求不得互相覆盖。
- 点击“允许一次”后先显示等待确认，只有 DSH 明确回应成功才视为成功。
- 任何 UI 风险提示都是辅助，不得替代完整参数。

### 2.4 简约的硬约束

- 常态 UI：**一个主体玻璃容器，常规任务不得出现深色子容器**。
- 同屏主视觉焦点：不超过 1 个；审批出现时焦点切换到审批入口。
- 常态字体：以 13~16 px 为主，标题不使用夸张粗体；过长时省略且可展开阅读。
- 无审批时没有常驻工具类型 Badge；没有空状态说明段落堆叠。
- 操作区域不能被滚动条裁切；点击区域建议至少 40 px 高。

## 3. 玻璃材质规范：禁止磨砂灰塑料

### 3.1 视觉关键

在真实桌面上，玻璃主体应呈现：

- **弱主体染色**：背景的色彩与明暗仍可感知，而不是统一灰色调；
- **局部柔和散射**：可以适当模糊背景，但不能把背景完全熔成单一灰泥；
- **薄而亮的边界**：1 px 左右的精致轮廓 + 角部较明显的反射，不采用厚灰边；
- **极弱色散**：仅局限于玻璃弧边，少量冰蓝、暖金、淡紫；
- **明暗自适应**：背景明亮时文字自动保证对比度，背景深暗时保持同样可读。

> 玻璃“通透”不等于将主体所有像素都做成 alpha=0，也不等于使用 blur=0。最终以“桌面背景层次仍可感知 + 文字清晰”作为目标。

### 3.2 颜色建议（仅作为启动 Token）

```css
:root {
  --glass-outer-radius: 28px;
  --glass-pill-radius: 999px;
  --glass-edge: rgba(255, 255, 255, 0.46);
  --glass-edge-highlight: rgba(255, 255, 255, 0.80);
  --glass-tint: rgba(210, 232, 252, 0.08);
  --glass-shadow: 0 15px 40px rgba(15, 30, 55, 0.12);
  --glass-blue: #75adfa;
  --glass-gold: #dca958;
}
```

以上数值不是视觉达标证明。**实际 alpha、blur、色调由桌面截图对比迭代确定；不可以凭设计稿推断 Windows 实现已经成功。**

### 3.3 渲染层严格分离

1. **Window substrate**：真正的 Windows 透明 / DWM 系统背景材料；
2. **Optical overlay**：轻量 CSS/SVG 细边、高光、局部受控反射；
3. **Content**：文字、当前步骤、进度、审批按钮。

只允许必要的视觉层。禁止 5~8 层全窗口 `backdrop-filter`、高成本全屏 shader 或持续晃动的渐变底图。背景材质作用于窗口/透明合成，`backdrop-filter` 只对 Web 内容合成有确定语义，不能当成跨其他应用的背景模糊保证。

### 3.4 Mica、Acrylic 与 Liquid Glass 的边界

- **Mica** 偏向使用桌面背景/主题生成窗口材质，不是用户期望的动态窗后透视；不优先用它作为“透明水晶”目标。
- **Acrylic** 可以提供 Windows 背景模糊的原生质感，但不保证轻薄、明亮，也不自动产生苹果式的动态折射。
- **Tauri 2** 可以调用 Windows 窗口特效，但没有自动的“Windows 版 iOS Liquid Glass”渲染器。
- **强折射和焦散** 在参考渲染图中可以被美术化夸张；真实应用需先追求轻薄透明和稳定交互，不必硬追过度镜头光晕。

## 4. 灵动交互，而非窗口突然放大

| 事件 | 要求 | 验证方式 |
|---|---|---|
| 胶囊→速览 | 外轮廓连续平滑伸展，内容依次渐入 | 录屏逐帧观察，无闪烁裁切 |
| 速览→胶囊 | 先退内容，再收容器；不闪回旧布局 | 连续 20 次切换 |
| 审批到达 | 柔和暖色提示；按配置自动展开或只加数量徽标 | 多种设置组合 |
| 鼠标悬停 | 边缘微弱高光变化，无全窗口亮度大跳 | 白/暗壁纸测试 |
| 鼠标拖拽 | 不误触展开，不错位，吸附不跳跃 | 125%/150% DPI |
| 手动缩放 | 断点布局重排，不放大字体/图标到失真 | 从最小到最大连续拖动 |
| 提交审批 | `pending → submitting → confirmed/failed` | 断线、请求撤销、重复点击 |
| 关闭动效 | 尊重系统减少动态效果和用户设置 | 设置开关/系统模式 |

**实现提醒：** React 内部元素的弹簧动画与原生窗口 bounds 动画是两件事。必须研究 `BrowserWindow` 真实尺寸变化对 Web 内容的裁切和 Windows 背景模糊性能的影响。如果强制连续改变原生窗口尺寸造成掉帧，应重新组织动效（例如内容渐显与谨慎的窗口 resize 策略），不能靠增加动画时长遮掩卡顿。

## 5. 第一次也是最后一次 Electron 集中整改

> **范围限制**：这是一轮完整重构，不再把小调 CSS 计作单独“迭代成功”。完成后立即验收；效果仍一般则转 Tauri 2 对照实验。

### E0 · 基线/根因审计（必须先完成）

- [ ] 找出 Electron `BrowserWindow` 创建参数：`transparent`、`frame`、`backgroundColor`、`backgroundMaterial`、`resizable`、`roundedCorners`、阴影等；
- [ ] 找出 DWM/Windows 原生背景处理代码与第三方特效包；
- [ ] 排查 `html`、`body`、React 根节点、容器是否有不透明背景；
- [ ] 排查所有深蓝/深灰大面积背景 class、嵌套 `backdrop-filter`、半透明覆盖层；
- [ ] 验证 Windows 版本与 DWM 特效接口适用条件；
- [ ] 在相同壁纸下捕捉现有 `capsule`、`peek`、`expanded`、`approval` 图；
- [ ] 记录审批裁切原因（布局 `overflow`、固定高度、嵌套滚动还是窗口 bounds 不匹配）。

输出 `reports/visual-baseline.md`，在报告中写明“原来真正的背景绘制路径”，不要只贴参数。

### E1 · 玻璃底层 A/B 实验（先于精修 UI）

以相同 UI 内容、相同 Windows 背景和窗口尺寸进行：

- **A**：原当前实现（对照）；
- **B**：Windows 透明窗口 + 最小背景填充（验证真透明与阴影/圆角）；
- **C**：可用时启用 Electron 原生 Acrylic（验证窗口材质与实际透明感）；
- **D**：B/C 中更好的方案 + 1 px 精细光学边缘与必要局部文字承载层。

每种方案分别在浅色、深色、复杂壁纸/窗口背景下保存真实截图。记下是否出现白边、灰蒙、阴影缺失、圆角直角、前后台状态变化、移动/缩放时卡顿。

**硬条件：禁止在材质试验阶段加入深色背景卡片。**

### E2 · 删除错误信息层级

- [ ] 删除应用品牌栏和底部连接成功栏；

## 6. 可执行的验收标准（Gate A）

### 6.1 直接否决项：出现任一项即本轮不通过

- 常态仍有深蓝/深灰大面积实心框嵌套；
- 主体仍然明显是混浊灰色塑料/厚磨砂，而不是轻薄、带背景层次的玻璃；
- 审批按钮任何情况下被裁切/遮挡或与请求错绑；
- 点击允许只改 UI 而没有真实 DSH 确认；
- 存在真实任务状态被 Mock 或硬编码覆盖；
- 透明效果靠使用静态背景截图冒充，或程序未经允许读取桌面图像；
- 拖拽/缩放引发明显黑闪、窗口残影、不可交互、频繁卡死。

### 6.2 视觉评分（100 分；由用户根据真实截图确认）

| 项目 | 分值 | 评分依据 |
|---|---:|---|
| 透明与轻薄感 | 25 | 背景颜色和空间层次可见，没有灰泥感 |
| 单块玻璃一致性 | 20 | 无深色内嵌大卡片、分层统一 |
| 轮廓高光与精细度 | 15 | 细边缘、微反射，不是粗描边/霓虹 |
| 极简信息组织 | 15 | 只有任务、进度、当前步骤、审批入口 |
| 灵动形变 | 15 | 连续、流畅、自然、不闪跳 |
| 多背景下可读性 | 10 | 浅/暗/复杂背景都能阅读内容 |
| **合计** | **100** | |

**视觉通过门槛**：总分 **≥85/100**，其中“透明与轻薄感”至少 **20/25**，“单块玻璃一致性”至少 **17/20**，且用户认可整体观感。若用户明确认为“仍然一般”，无论分数如何均视为不通过。

### 6.3 功能/稳定性独立门槛（必须全部通过）

- [ ] Todo 真实状态、会话切换、Mock/真实模式区分正确；
- [ ] 存在已知审批请求时不会被其他请求覆盖；
- [ ] 审批按钮始终可见，确认/拒绝结果以 Bridge 实际回应为准；
- [ ] 断线/重连没有误批准和过期按钮；
- [ ] 拖动/调整大小/置顶/托盘/退出功能可用；
- [ ] 100%、125%、150% DPI 下布局无明显溢出；
- [ ] 10 分钟工作场景内无致命渲染错误；
- [ ] 动画无持续占满 CPU/GPU 的循环特效。

**性能记录**：提供运行平台和测量方法，记录空闲 5 分钟平均 CPU/工作集、连续 20 次展开/折叠的响应与掉帧、拖拽/缩放体验。不要在没有测量工具的情况下编造 FPS/百分比。

### 6.4 Gate A 决策

```text
本轮 Electron 集中整改结束
        │
        ├── 视觉 ≥85 且无 P0 问题、用户认可
        │      └── 保留 Electron，继续完善业务功能
        │
        └── 否则（含用户仍觉得“很一般”）
               └── 停止 CSS 微调，进入 Tauri 2 技术对照 Gate B
```

**不能把 Gate A 不通过重新定义成“再优化几个参数就行”。** 用户已经连续反馈多次，必须执行技术路线升级评估。

## 7. Electron 的最后一轮技术排查清单

下列选项是“应当检查的接口/能力”，不是强制推荐的某一固定配置。

1. 当前 Electron 版本是否支持 `BrowserWindow.setBackgroundMaterial('acrylic')`：官方标注 Windows 11 22H2+；先检查系统版本。
2. `backgroundMaterial`、`transparent`、`backgroundColor`、`frame`、窗口阴影和 Web 根元素背景之间是否发生冲突。
3. 样式上是否存在 `bg-slate-*` / `bg-zinc-*` / `#26394d` 等高不透明度背景直接盖住底层材质。
4. 透明窗口是否在不聚焦和被其他程序遮挡后发生视觉变化。
5. `BrowserWindow.setBounds()` 频繁调用与背景材质计算是否相互导致卡顿。
6. React 的 `backdrop-filter` 是否仅模糊了 DOM 背景，而没有真正处理别的桌面窗口。
7. 是否使用多个真实 OS 窗口造成不同的边框/阴影与焦点行为。

**如果报告显示 Electron 的原生合成已经正确运行，但最终仍无法提供需要的光学效果，不能继续仅更换颜色和 blur。应直接进入 Gate B。**

参考：Electron 官方 BrowserWindow 文档 https://www.electronjs.org/docs/latest/api/browser-window

## 8. Gate B：Tauri 2 的独立对照原型（必须真机）

> Tauri 2 是明确的候选技术栈，**但不能在没有证据时断言它一定比 Electron 更通透**。底层系统合成、Windows 版本、GPU 驱动、样式覆层都会影响结果。

### 8.1 实验目录

```text
experiments/
  tauri-glass/
    src/                  # React UI，尽量复用 Electron 对照中的组件与 Tokens
    src-tauri/            # Rust / Tauri v2 壳层
    reports/
      matrix.md
      screenshots/
      performance.md
      verdict.md
```

先只做**单窗口原型**，不得立刻重写整个 DSH 通信、审批和业务 Store。原型只实现同一份 Mock 数据（标题、1/2、当前步骤、审批入口）、同一目标尺寸、同一组背景和基础拖拽缩放。

### 8.2 三组材质实验

- **T1**：Tauri 2 透明窗口 + 透明 HTML/body + 极轻 UI 覆层；
- **T2**：Tauri 2 `setEffects` 中的 Acrylic / 适用 Windows 特效，记录真实结果；
- **T3**：T1/T2 中效果更好的材质 + 同 Electron 一致的薄轮廓/高光/排版；
- **E**：整改后的 Electron 版本，作为严格同条件对照。

同环境比对：

- 完全相同的任务内容/字体/尺寸；
- 同一台电脑、同样 DPI、相同壁纸和屏幕背景；
- 同时测试窗口聚焦和失焦；
- 测试拖动、手动缩放、自动胶囊变形；
- 对比真实截图、录屏、资源占用；
- 检查圆角、抗锯齿、阴影、白边/黑边和焦点切换。

### 8.3 Tauri 2 文档明确的条件

- `setEffects()` 可施加平台窗口材质；**窗口和 HTML 页面必须允许透明**，否则网页自己的背景会遮挡原生材质。
- Windows 部分装饰/阴影配置可能与特效互相影响，需要根据 Tauri 2 官方备注做验证。
- `window-vibrancy` 的公开说明列出某些 Windows 组合在拖动或缩放时可能产生性能问题，因此必须实测，不能假设 Tauri 原生性能必胜。
- 不应把 macOS 上可用的 Liquid Glass API 误写成 Windows 可调用的同名系统功能。

参考：

- Tauri v2 `setEffects`：https://v2.tauri.app/reference/javascript/api/namespacewebviewwindow/
- `window-vibrancy`：https://github.com/tauri-apps/window-vibrancy

### 8.4 Gate B 迁移标准

**建议迁移条件：**

1. Tauri 实机截图在**透明、薄边、无厚磨砂**三个核心视觉指标上明显优于 Electron；
2. 对照完成后用户认可 Tauri 方向；
3. 拖动、缩放、置顶、恢复、DPI 切换无阻断问题；
4. 资源开销不出现明显劣化，空闲不会持续渲染；
5. 关键产品能力都存在可实现路径：托盘、窗口权限、Bridge 通信、审批入口、异常处理。

**若 Tauri 只是“略好一点”，但仍旧灰蒙、没有清澈感，不得仓促迁移。** 在 `verdict.md` 中明确问题属于 DWM 材质限制、WebView 叠层限制还是自定义光学能力缺失，提出是否需要使用更底层的 Rust/Win32 + GPU 渲染方案，而不是继续换框架碰运气。

## 9. Tauri 2 迁移计划（Gate B 通过后执行）

### 9.1 保留与替换

| 模块 | 迁移策略 |
|---|---|
| React + TypeScript 组件 | 尽量保留，只重写窗口原生 API 绑定 |
| Zustand / 任务 UI Store | 保留，不修改业务语义 |
| Framer Motion / 动画 | 保留前端元素动画；原生窗口尺寸动画需要适配 |
| DSH Bridge / WebSocket / 协议 | **保持独立**，不在迁移时重写 DSH 审批机制 |
| Electron Main / Preload | 迁移到 Tauri Rust 命令、事件和权限控制 |
| 托盘 / 右键菜单 / 快捷键 | 使用 Tauri 2 对应插件或 Rust 实现并测试 |
| 透明窗口 / 背景特效 | Windows 原生方案，由 Tauri 壳层管理 |
| 记录、调试与 Mock | 保留，确保迁移前后同一数据快照可复现 |

### 9.2 必须先创建抽象层

前端不允许到处直接调用 Electron 或 Tauri API。先定义通用端口，例如：

```ts
export interface GlassWindowPort {
  expand(mode: 'capsule' | 'peek' | 'expanded' | 'approval'): Promise<void>;
  setAlwaysOnTop(value: boolean): Promise<void>;
  showContextMenu(): Promise<void>;
  focusOriginalDSH(sessionId?: string): Promise<void>;
}

export interface GlassConnectionPort {
  getSnapshot(): Promise<unknown>;
  subscribe(listener: (event: unknown) => void): () => void;
  // 审批仍由既有的权限/会话路由验证，禁止在 UI 里直接发送未经校验的批准。
}
```

具体类型应以仓库已有协议替换 `unknown`；这里只表达**外壳解耦原则**。

### 9.3 迁移顺序

1. 新建 `apps/desktop-tauri/` 或同类目录；原 Electron 保留可回滚。
2. 移植 GlassWindow 组件和视觉 Tokens；通过 mock 完成布局对照。
3. 实现 Rust 壳层：无边框、透明、拖拽、缩放、托盘、置顶、开机启动（若现有产品要求）。
4. 对接已存在的独立 Bridge，不改变协议含义与事件顺序。
5. 完整接入 Todo / Session 状态；校验离线与重连。
6. 接入审批/用户问题交互，重点测试多会话、并发、请求取消、提交确认和错误回退。
7. 在 Windows Release 构建中测试而非仅在开发模式运行；测量前台/后台/托盘状态。
8. 通过功能和视觉回归，得到用户批准后，将 Tauri 设为默认桌面入口；Electron 暂作回滚版本。

**迁移期间禁止做无关重构**，例如同时重写协议、替换状态管理、修改 DSH 插件机制；否则无法判断故障来自迁移还是业务变化。

### 9.4 迁移失败回退

- 如果 Tauri 影响审批可靠性、窗口事件或存在严重渲染问题，暂停上线，保留 Electron 可用版本。
- 将失败原因记录在 `reports/tauri-verdict.md`，并按需要评估更底层原生 UI/GPU 合成，不再在两个框架之间反复切换。

## 12. 资料与局限性

- Electron BrowserWindow：<https://www.electronjs.org/docs/latest/api/browser-window>
- Tauri 2 Window/WebviewWindow：<https://v2.tauri.app/reference/javascript/api/namespacewebviewwindow/>
- Tauri window-vibrancy：<https://github.com/tauri-apps/window-vibrancy>

**事实与推断区分：**

- “当前看起来磨砂、深卡片突兀、审批按钮裁切”是从用户提供截图**直接观察**到的问题。
- “根因是某条 CSS / 某个 Electron 参数”目前仅是假设，须经过 E0 的代码审计验证。
- “Tauri 比 Electron 视觉更好”是**待实验验证的假设**，不是框架固有保证。
- 理想参考图是生成的概念图；目标是实现**真实可用、接近其设计语言的桌面 UI**，不能把渲染图效果当作未经验证的性能或光学承诺。

**一句话决策**：**修好一次；真实桌面验收。仍旧混浊或笨重，就停止 Electron 的重复美化，转做 Tauri 2 的同条件对照；胜出才迁移。**
