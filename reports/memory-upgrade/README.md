# 内存开销优化 — 2026-10-20

保持玻璃分辨率、取样范围与调度、RGB 色散、窗口形变、会话/审批功能，减少重复帧、临时像素分配和退休滤镜资源。

## 实现

- 取样助手复用当前尺寸的 Bitmap、RGBA 与上一帧缓冲。尺寸改变时清零并释放旧缓冲，不保留最大尺寸；停止时清零。Graphics 仍在每次读像素前结束绘制。
- 只有捕获范围、窗口几何和全部 RGBA 字节都完全相同时才跳过完整帧传输。仍按原调度取样和验证 HWND/PID/显示亲和性，无哈希误判、像素容差、降分辨率或降采样率。
- 新订阅、页面重载和外观设置变更会合并请求强制新帧，保证静止背景下首次显示、主题/文字配色和恢复正常。
- 主进程复用精确尺寸缓冲，发送原字节视图，取消一次整帧复制；同步 IPC 序列化后清零本地像素。停止时释放缓冲。
- 原生形变复用同一组 SVG 折射节点，更新贴图、尺寸和三路系数；位移图计算后立即释放临时 Canvas；停止取样时 Canvas 背板归零。

## 测量方法与范围

基线为提交 `fe5a7af` 的独立源码快照与构建，候选为本次修改；同一 Electron 44.8.0、同一台 Windows、实际 150% 显示缩放。使用生产构建、独立临时配置，不接触用户 DSH Profile。

`memory-audit.mjs` 每个场景预热 5 秒，再采 4 次；前后各两轮。主指标为 Windows `WorkingSetPrivate` 的进程组总和（MiB），同时记录私有提交、各进程、Node external、JS heap 和真实 Canvas 绘制计数。不将共享工作集反复相加，也不把 GPU 专用显存算作进程私有 RAM。没有强制 GC、裁剪工作集或禁用 GPU/沙盒。

也未周期性调用 [`webFrame.clearCache()`](https://www.electronjs.org/docs/latest/api/web-frame#webframeclearcache)：官方说明盲目清空缓存可能使应用因重新填充缓存而变慢。本轮回收的是已失效的具体像素/绘制对象。

为固定实际输入，两侧都包含同一个 800×600 DIP 的受控背景窗口及其额外 renderer（约 20 MiB）；GPU 进程也包含它的固定合成开销。因此表中绝对值不是用户安装版任务管理器的直接预测。持续变化场景每 180ms 改变真实背景颜色；视频等每帧都变化的背景不能获得相同的去重收益。早期未能验证背景覆盖的独立 WinForms 试验不用于最终对照。

测量表与完整统计见 `comparison.json`；原始记录为 `controlled-before-1/2.json`、`after-1/2.json`。

| 场景 | 优化前中位数 | 优化后中位数 | 变化 |
| --- | ---: | ---: | ---: |
| 未取样胶囊 | 288.6 MiB | 275.8 MiB | -4.5% |
| 静止背景、胶囊 | 370.3 MiB | 248.5 MiB | **-32.9%** |
| 静止背景、展开 | 397.8 MiB | 319.1 MiB | **-19.8%** |
| 每 180ms 变化的背景、展开 | 383.7 MiB | 360.3 MiB | -6.1% |
| 18 次形变后展开 | 692.2 MiB | 627.0 MiB | -9.4% |
| 上述操作后收回胶囊 | 599.9 MiB | 623.2 MiB | **+3.9%** |
| 隐藏后 | 522.8 MiB | 443.4 MiB | -15.2% |

稳定收益主要来自静止画面不再反复创建/传输/上传像素。未取样阶段的差异很小，不据此归因全部运行时内存改善。动态背景收益较小；反复形变再收起的组合样本反而高约 23 MiB，该场景未获得稳定改善。此时 GPU 进程的驻留缓存仍占大头，不能把图像缓冲优化描述成已经解决图形驱动缓存问题。隐藏阶段两轮也有明显波动，表中为合并样本中位数。

矩阵测量完成后，末次增加了“Main 因快速移动拒绝该帧时，下一次强制重取”的保护；最终构建另外完成了快速移开/移回与完整视觉/取样回归。没有将这行保护计为额外内存收益，也未声称重新测完最后构建的整个四轮矩阵。

## 功能与视觉验证

- `pnpm build`（包含同版原生助手）、lint、typecheck、15 文件 142 单测通过。
- `pnpm test:memory`：清透/磨砂 × 胶囊/速览/展开/审批共 8 组，所有输入 RGBA 字节、SDF 贴图、RGB 系数和截图 SHA-256 前后完全一致。发送后立即清零源缓冲，接收端仍保留完整序列化快照。
- 最终构建的真实限定区域取样：静止背景停止重复上传；三个原生背景颜色变化约 61–104ms 到达观测端；16ms 更新的背景在 1.2 秒内接收 23 张变化帧。该计数是输入到达，不是 GPU 呈现 FPS。
- 原生移动（即使背景为同色）、六次形变、晚订阅、静止画面调色、页面重载、隐藏/恢复、实色切换与画布释放通过。见 `native-acceptance.json`。
- 既有性能功能回归、动效与审批布局/队列/断线只读回归通过。三帧像素回归改用真实位置变化，避免将重复帧数量当成功能要求。
- 原有完整原生光学验收通过：真实灰阶条纹保留 24–238 对比、零彩色污染；变化几何下输入到达约 16.2Hz；四形态、隐藏恢复、实色停止、助手故障安全停用与重启恢复通过。见 `bounded-capture-acceptance.json`，不将它称作屏幕呈现帧率。
- 额外尝试的连续鼠标拖动旧脚本没有通过：先修正其默认过程页/步骤页、旧命令类名和 Mock 审批计时的夹具前提后，基线 `fe5a7af` 同样在展开态只移动 6 DIP，未满足至少 20 DIP 的连续拖动断言。保留断言，不把该结果算作实际鼠标拖动验收；本轮已通过的是原生窗口移动/几何与图像恢复。真实鼠标操作需人工复核。

## 复现与人工检查

完整构建后运行 `pnpm test:memory`。分别将 `GLASS_AUDIT_APP` 指向独立旧版与本次构建的 `apps/desktop`，运行 `node scripts/memory-audit.mjs controlled-before-1`（各轮标签不同）；本次默认路径可运行 `node scripts/memory-audit.mjs after-1`。四轮齐全后运行 `node scripts/compare-memory.mjs`。

人工检查：在静止图片和播放中的视频前拖动、展开/收起；修改底色/浓度/亮度与主题；隐藏后恢复；切换会话并检查过程、轮数/步数、审批与问答。真实用户 DSH Desktop 审批、多屏及所有 GPU/DPI 组合没有因本轮测试获得新的验收结论。

Electron 基础运行时与图形驱动缓存仍占较大部分，当前优化不构成固定内存上限。已安装的 npm/Release 0.2.3 运行包不会随源码构建自动更新；新 JS 与支持 `frame-force` 的原生助手必须一起打包。
